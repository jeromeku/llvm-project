## Key Terms

- `_ods_ir`: Alias to the native C++ extension submodule `mlir._mlir_libs._mlir.ir` (exposes Operation, OpView, Type, Value, …).
- `_ods_common`: Pure Python helpers used by generated files (argument coercion, segmented accessors, result/value dispatch, etc.).
- `_{DIALECT}_ops_gen.py`: Auto‑generated OpView subclasses and Dialect wrapper for a dialect; registers ops/dialect with the runtime.

## Purpose of _{DIALECT}_ops_gen.py

- Generated by CMake/macros around `mlir-tblgen -gen-python-op-bindings`:
  - Path shape is computed here: [mlir/cmake/modules/AddMLIRPython.cmake:314](mlir/cmake/modules/AddMLIRPython.cmake#L314).
    See: [mlir/cmake/modules/AddMLIRPython.cmake:314](mlir/cmake/modules/AddMLIRPython.cmake#L314)
  - Emitted by tblgen with `-gen-python-op-bindings -bind-dialect=…`:
    See: [mlir/cmake/modules/AddMLIRPython.cmake:319](mlir/cmake/modules/AddMLIRPython.cmake#L319)
- Contains:
  - A `Dialect` subclass for the dialect, decorated with `@register_dialect`.
  - An OpView subclass per op, decorated with `@register_operation(_Dialect)`.
  - Class-level metadata for variadic segments and regions (`_ODS_*`).
  - A default builder that wires operands/attributes/results and inserts the op (optionally inferring types).
  - Properties for named operands/results/attributes/regions.
- The text it generates is defined here (templates shown below). These are emitted into `_{dialect}_ops_gen.py`:
  - File header imports and aliases `_ods_ir = _ods_cext.ir`:
    [mlir/tools/mlir-tblgen/OpPythonBindingGen.cpp:23-44](mlir/tools/mlir-tblgen/OpPythonBindingGen.cpp#L23-L44)
  - Dialect and OpView class templates:
    - Dialect: [mlir/tools/mlir-tblgen/OpPythonBindingGen.cpp:48](mlir/tools/mlir-tblgen/OpPythonBindingGen.cpp#L48)
    - OpView: [mlir/tools/mlir-tblgen/OpPythonBindingGen.cpp:62](mlir/tools/mlir-tblgen/OpPythonBindingGen.cpp#L62)

## Common Usage

Extending an existing op (Python-side overrides)

- You can “specialize” a generated OpView by re‑declaring it with the same name and decorating it with `@register_operation(..., replace=True)`.
- Example: `arith.constant` provides a more convenient constructor and helpers:
  - [mlir/python/mlir/dialects/arith.py:1](mlir/python/mlir/dialects/arith.py#L1)
  - The extension itself (selected lines): [mlir/python/mlir/dialects/arith.py:15-72](mlir/python/mlir/dialects/arith.py#L15-L72)

  @_ods_cext.register_operation(_Dialect, replace=True)
  class ConstantOp(ConstantOp):
      def __init__(self, result_or_attr, value=None, *, loc=None, ip=None):
          # Accept ints/floats/arrays or a prebuilt Attribute.
          # Dispatches to the base generated builder.
          ...

  def constant(result_ty, value, *, loc=None, ip=None) -> Value:
      return _get_op_result_or_op_results(ConstantOp(result_ty, value, loc=loc, ip=ip))

Binding a new dialect

1) Define your ops in TableGen (`.td`).
2) Hook up Python bindings via CMake:
   - Add a block like this to the Python package CMake (pattern):
     [mlir/python/CMakeLists.txt:60-84](mlir/python/CMakeLists.txt#L60-L84)
3) In `dialects/mydialect.py`, import generated symbols and (optionally) extend:

   from ._mydialect_ops_gen import *
   from ._mydialect_ops_gen import _Dialect

   # Optional: add convenience builders/properties here.

## Under the Hood: What Generated Modules Call Into

Registration decorators (C++ extension)

- The generated files use `@_ods_cext.register_dialect` and `@_ods_cext.register_operation(_Dialect)`.
- Those are defined in the native extension and populate a global registry used when materializing views from raw operations:
  - Decorators: [mlir/lib/Bindings/Python/MainModule.cpp:27-77](mlir/lib/Bindings/Python/MainModule.cpp#L27-L77)
  - Dialect/Op registration hooks: [mlir/lib/Bindings/Python/MainModule.cpp:78-115](mlir/lib/Bindings/Python/MainModule.cpp#L78-L115)
  - Registry implementation: [mlir/lib/Bindings/Python/IRModule.cpp:30-40](mlir/lib/Bindings/Python/IRModule.cpp#L30-L40), [mlir/lib/Bindings/Python/IRModule.cpp:107-126](mlir/lib/Bindings/Python/IRModule.cpp#L107-L126), lookups at [mlir/lib/Bindings/Python/IRModule.cpp:169-190](mlir/lib/Bindings/Python/IRModule.cpp#L169-L190)

OpView.build_generic → Operation.create → mlirOperationCreate → Operation::create

- In the generated class, builders call into `_ods_ir.OpView.build_generic(...)`.

## What are _ods_common.* helpers?

- Pure-Python shims imported by every generated file. They:
  - Define segmented/equally-sized accessor helpers for variadic groups
  - Provide value/result dispatchers so builders can accept `OpView`, `Operation`, `Value`, lists of values, etc.
  - Bridge typed hints (`ResultValueT`, `MixedValues`, …) and utility dispatchers for common “mixed” forms used in dialects.
- Key functions and where they live:
  - `_cext = mlir._mlir_libs._mlir` import and `_ods_ir = _cext.ir` aliasing happens via the generator header; `_ods_common` imports typed Python names for annotations.
  - `segmented_accessor`: [mlir/python/mlir/dialects/_ods_common.py:31-49](mlir/python/mlir/dialects/_ods_common.py#L31-L49) — uses `_cext.ir.DenseI32ArrayAttr` to split a flat list into groups.
  - `equally_sized_accessor`: [mlir/python/mlir/dialects/_ods_common.py:51-73](mlir/python/mlir/dialects/_ods_common.py#L51-L73)
  - `get_op_result_or_value`, `get_op_results_or_values`, `get_op_result_or_op_results`: [mlir/python/mlir/dialects/_ods_common.py:75-130](mlir/python/mlir/dialects/_ods_common.py#L75-L130), [mlir/python/mlir/dialects/_ods_common.py:132-162](mlir/python/mlir/dialects/_ods_common.py#L132-L162)

## What is _ods_ir.* (e.g., OpView) bound to?

- `_ods_ir` is just `_ods_cext.ir`, where `_ods_cext` is the native extension module `_mlir` and `.ir` is its IR submodule.
- The IR submodule is created here: [mlir/lib/Bindings/Python/MainModule.cpp:137-148](mlir/lib/Bindings/Python/MainModule.cpp#L137-L148), with its classes populated in `populateIRCore` and friends.
- Notable bindings:
  - `OpView` class and its core constructor/builders: [mlir/lib/Bindings/Python/IRCore.cpp:3561-3645](mlir/lib/Bindings/Python/IRCore.cpp#L3561-L3645), with the generic builder implemented at [mlir/lib/Bindings/Python/IRCore.cpp:1686-2040](mlir/lib/Bindings/Python/IRCore.cpp#L1686-L2040).

## Practical Tips and Patterns

- Extend vs. replace: Prefer adding convenience methods in your `dialects/foo.py` by re‑decorating the generated class with `replace=True`. Keep base ODS‑derived properties intact.
- Variadic segments: If an op has variadic operands or results, the builder manages the segment sizes for you by adding `DenseI32ArrayAttr` attributes (`operandSegmentSizes`/`resultSegmentSizes`). See the merge code at [mlir/lib/Bindings/Python/IRCore.cpp:1968-2012](mlir/lib/Bindings/Python/IRCore.cpp#L1968-L2012) and helper `segmented_accessor` at [mlir/python/mlir/dialects/_ods_common.py:31-49](mlir/python/mlir/dialects/_ods_common.py#L31-L49).
- Location/insertion defaults: If you don’t pass `loc`/`ip`, they are resolved from the Python thread‑local stack or traceback (when enabled):
  - Defaulting and error when missing: [mlir/lib/Bindings/Python/IRCore.cpp:1040-1088](mlir/lib/Bindings/Python/IRCore.cpp#L1040-L1088)
  - Traceback-based locations: [mlir/lib/Bindings/Python/IRCore.cpp:2810-2860](mlir/lib/Bindings/Python/IRCore.cpp#L2810-L2860)
